# PCK integration proposal

The repository currently contains a workflow scaffold only; no runtime, UI kit, backend, CI, app-level package manager or storage. Phase 1 should create `apps/font-lab-web/` (minimal browser workbench), `services/font-build/` (isolated Python compiler) and a small shared schema package only when the vertical slice needs it. `.progressive/` continues to own project plan/ADRs/handoff; product JSON is not a replacement for PCK state.

Preview geometry: browser evaluator on a Worker for responsive local controls; compiler service independently validates source and emits fonts. Begin with local CLI/worker invocation in development, then choose a job transport for hosted deployment based on real traffic; do not add a queue prematurely. Each export job gets a random isolated directory, hard timeout, memory/CPU/output limits and cleanup in `finally`; store immutable downloadable artifacts by source hash with bounded retention. Browser caches recipe evaluations by (engine version, glyph, axes, switch); server caches successful font artifacts by full project/export/compiler digest. Cache errors briefly or not at all.

Input security: Phase 1 project JSON only; no arbitrary uploaded font files. If later introduced, set documented size cap (initial proposal ≤10 MB compressed, ≤50 MB expanded), MIME/magic validation, decompression and glyph/table limits, no path traversal, sandboxed parsing process, no outbound network, resource quotas and antivirus/format fuzzing. Never execute user expressions in recipes. Keep temp/export storage private and avoid embedding user text or source payload in logs. Rate-limit remote builds when hosted. Dependency isolation: pinned Python venv/lock and JS lockfile, separate from PCK tools. CI: source-schema tests, geometry invariant tests, two-master build smoke test, font table validation, Latin/Cyrillic shaping snapshots, browser interaction tests; run PCK audit. Future agents consume `research-summary.json`, ADRs and PCK context compile, not copied repository manuals.

The proposed browser Worker vs server split is an ADR because identical recipes must be deterministic in both contexts. Phase 1 may start with browser preview plus Python export from the same versioned project source; parity tests compare a glyph sample at named coordinates.
